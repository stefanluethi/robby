# Trace link: sonde vs protobuf, summary

Short version of the [benchmark report of 2026-10-26](results-2026-10-26.md). The link is
USART2 at 1 Mbaud 8N1, so at most **100 kB/s**. The IMU produces **806 samples/s**.

## UART (STM32 → ESP32)

| | sonde (decimated by 2) | sonde (all samples) | protobuf (all samples) |
|---|---:|---:|---:|
| IMU samples/s delivered | 403 | 521 of 806 | **806** |
| bytes per IMU sample | 159 (3 messages × 53 B) | 159 | **~7** |
| bytes per IMU sample, all traces included | 171 | 159 | **10.1** |
| average bytes per message¹ | 55.6 | 53.0 | **9.5** |
| UART throughput | 69.0 kB/s | 83.0 kB/s | **8.2 kB/s** |
| UART usage | **69 %** | **full** (other traces stop) | **8 %** |
| headroom | 31 % | none (35 % of samples lost) | **92 %** |

¹ All messages on the link divided by their count. With sonde one IMU sample is three
messages (`imu/acc/x`, `/y`, `/z`); with protobuf it is one `imu/acc` record.

**Headroom.** sonde would need ~128 kB/s (128 % of the UART) to carry all 806 samples/s.
Protobuf carries them in 8 %. In the ramp the UART reached 85 % (where the STM32 starts
dropping records) at about **11–12k samples/s, ~14× today's stream**. The UART is no longer
the limit: the ESP32 saturates first (below).

## WiFi (ESP32 → blip, CBOR over WebSocket)

blip's CBOR protocol is unchanged. With sonde the bridge forwarded the CBOR from the UART
1:1. With protobuf the outpost translates to CBOR, so WiFi carries more than the UART.

| | sonde (decimated by 2) | protobuf (all samples) |
|---|---:|---:|
| WiFi throughput | 69.0 kB/s | 61.2 kB/s |
| bytes per IMU sample on WiFi | 159 | 68 |
| WebSocket frames/s | 73 | 22 |
| share of the WiFi limit (607 kB/s clean) | 11 % | **10 %** |
| share of the WiFi peak (~700 kB/s) | 10 % | **9 %** |

Limits measured on the ESP32-C6 at the robot's usual spot (RSSI −58 to −64 dBm):

| | clean up to | saturates at |
|---|---:|---:|
| WiFi alone (outpost generates the data, no UART) | 8k samples/s, 607 kB/s | ~700 kB/s (≈ 5.6 Mbit/s) |
| whole chain (UART → outpost → WiFi) | ~5.8k samples/s, 440 kB/s | ~7k samples/s, ~530 kB/s |

The chain stops ~25 % below WiFi alone because the ESP32 CPU is full (next section).
Today's stream uses **~1/7 of the chain's clean capacity**.

## ESP32 CPU load

There are no ESP32 CPU numbers for sonde: the baseline bridge firmware has no CPU counter.
The protobuf outpost reports `outpost/cpu_idle` every second:

| load | ESP32 CPU busy | WiFi kB/s |
|---|---:|---:|
| normal stream (806 samples/s) | **18 %** | 61 |
| + 1k synthetic samples/s | 32 % | 137 |
| + 2k | 46 % | 213 |
| + 3k | 61 % | 289 |
| + 5k | 85 % | 440 |
| + 7k requested (6.2k delivered) | **96 %**, queue drops | 535 |

The CPU (receiving and checking the UART, translating to CBOR, WiFi) is the bottleneck of
the protobuf chain. The UART is at only 60 % when the CPU saturates.
